## 1. 托盘后台长期稳定性

**状态：待验证**

### 历史现象

程序隐藏到后台运行一段时间后，托盘图标曾出现无法恢复窗口、无法退出的问题。

### 当前处理

- 关闭窗口改为隐藏到托盘，录制和监听继续运行。
- 调整托盘注册、窗口恢复、单实例和退出流程。
- worker 录制任务与 GUI 生命周期进一步隔离。

### 下一步

- 连续运行至少 24 小时。
- 验证多次隐藏/恢复、锁屏、睡眠和唤醒后的托盘操作。
- 若再次失效，记录发生时间、进程状态和此前操作。

## 2. 强制 Cookie 状态检查批量超时

**状态：待验证**

### 现象

强制 Cookie 主播会跳过 OAuth，直接走 TwitCasting 旧版网页状态接口 `streamserver.php`。当同一批主播在同一分钟集中检查时，旧接口可能连续超时，导致这些主播同时进入异常状态；未强制 Cookie 的主播因为优先走 OAuth，通常不受影响。

### 当前处理

- 旧版状态接口遇到超时会短暂等待后自动重试一次。
- 强制 Cookie 状态检查增加稳定错峰，减少同批主播同时请求旧接口。
- 强制 Cookie 的状态检查超时会先按瞬时网络异常累计；连续多次失败后才标记为异常。

### 下一步

- 使用开启强制 Cookie 的主播列表连续运行至少 3 小时。
- 观察是否还会出现同一批主播同一时间全部超时。
- 若仍集中超时，继续提高 Cookie 检查间隔或增加更细的队列化检查。

## 3. 强制 Cookie 下的离线假阳性

**状态：待验证**

### 现象

少数主播没有开播时，TwitCasting 旧版状态接口仍可能返回直播候选和 `.m3u8` 地址，真实媒体服务器随后返回 `404 Not Found`。

### 当前处理

- 强制 Cookie 主播连续两次出现访问类错误后，会进入受限直播状态并停止本场直播的重复录制尝试。
- 已修复独立 worker 在受限状态下每轮检查又把状态刷回“监听中”的问题。
- 本场直播识别改为只有两个明确且不同的 `movie_id` 才视为新直播；`created` 或 `current-live` 等不稳定标识继续按同一场压制。
- 受限状态下会继续等待直播结束或出现明确新直播，不再重复启动 FFmpeg。

### 尚未明确

- 返回 `404` 的候选究竟是受限直播、过期直播地址，还是旧接口的离线假阳性。
- 是否应在 FFmpeg 启动前增加 HLS 轻量预检，并将离线假阳性与无权限直播分开显示。

### 下一步

- 使用最新版观察对应主播离线时是否在两次失败后停止尝试。
- 保存状态接口返回中的 `movie_id`、`created` 和 HLS 地址特征，避免记录 Cookie。
- 根据真实样本决定是否增加“不可访问直播”独立状态。
- 验证会员限定但当前账号无权限时，GUI 是否稳定保持“受限直播”，且本场直播不再重复提醒。

## 4. OAuth 受保护直播提示抑制

**状态：待验证**

### 现象

OAuth `current_live` 明确返回 `is_protected=true` 时，旧逻辑会把它当成普通检查失败，导致同一场受保护直播期间每分钟重复输出错误。

### 当前处理

- 状态检查阶段已将 `is_protected=true` 归类为“受限直播：当前账号无观看权限”。
- 主进程调度和独立 worker 都会按同一场直播进行抑制，不再重复提醒或启动 FFmpeg。
- 直播结束后会自动恢复监听。

### 下一步

- 等下一次受保护直播真实出现时，确认 GUI 能保持“受限直播”，且日志只提示一次。

## 5. 鉴权自动策略边界

**状态：暂缓**

### 当前结论

- OAuth 用于官方 API 直播信息、`movie_id` 和评论。
- Cookie 用于网页会话权限及需要登录观看的直播。
- 普通公开直播没有必要全部强制携带 Cookie。
- 推荐保持全局 `auto`，只为确实需要的主播选择“强制 Cookie”。

### 尚未明确

- 哪些错误应触发从 OAuth/公开链路自动切换到 Cookie。
- Cookie 失效后是否应自动回退到公开录制。
- 是否需要展示每个主播本轮检测实际使用的鉴权链路。

## 7. 手动暂停后旧 worker 事件回流

**状态：待验证**

### 现象

主播正在直播时点击“暂停监听”，FFmpeg 会收到 `q` 并退出，历史记录也会写入 `manual_stopped`，但旧 worker 随后仍可能回传 `recording` 状态，使 GUI 又显示为“录制中”。

### 当前处理

- 暂停状态下忽略旧 worker 的状态、日志和错误事件。
- 暂停状态下仍处理最终 `result` 事件，确保手动停止历史记录不会丢失。
- 已增加单元测试覆盖“暂停后旧 worker recording 状态不得重新标记为录制中”。

### 下一步

- 使用正在直播的主播实测多次暂停，确认不会重新进入录制中。
- 观察暂停后是否仍能稳定写入 `manual_stopped` 历史记录。

## 8. 特定主播录制文件过大

**状态：待验证**

### 现象

大部分主播的录制文件体积正常，但少数主播由于直播码率、分辨率或 HLS variant 较高，录制成果明显偏大。

### 当前处理

- 历史记录新增平均码率展示，旧记录也可通过文件大小和时长估算。
- 新录制完成后会尝试用 FFprobe 写入分辨率、帧率、总码率、视频编码和音频编码。
- 全局和单主播均支持画质策略覆盖：原始/最高、高画质、中档稳定、低画质、自动尝试和仅保存音频。
- 可以把文件特别大的主播单独设置为“低画质”或“仅保存音频”，不影响其他主播。

### 下一步

- 用历史页观察高体积主播的平均码率和分辨率。
- 对比同一主播在中档稳定、低画质、仅保存音频下的文件体积和观看可用性。
- 确认“仅保存音频”是否适合作为长期归档策略；它主要减少成品文件体积，不保证降低代理流量。

## 9. 媒体进度看门狗真实场景验证

**状态：待验证**

### 现象

网络异常时可能出现只有录制运行时长、没有媒体时长和输出文件，或录制运行时长持续大幅领先媒体时长。旧看门狗会把 FFmpeg 重复输出的相同 `out_time` 误认为有效进度。

### 当前处理

- 只有媒体秒数实际增加才刷新进度时间，`00:00:00` 和重复时间戳不再续命。
- 首次有效媒体进度限时 90 秒；完全停滞阈值为 3 分钟。
- 相对落后超过 3 分钟并持续 45 秒也会触发回收。
- 回收后保留监听，10 秒后重新解析直播地址并自动恢复录制。

### 下一步

- 观察真实网络波动下是否能够生成新的续录片段。
- 确认正常 HLS 缓冲、时间戳跳变和低帧率直播不会被误判。
