# 录制稳定性对比与改造计划

本文记录与“ツイキャス録画君 Ver2.07”的后端处理差异，以及本项目后续稳定性改造方向。

## 1. 现象

当前 GUI 表面上支持多个主播同时录制，但在真实使用中容易出现：

- 多路同时开始时，某些直播录不上或录制进程异常退出。
- 后端和前端日志量过大，界面刷新与事件传递压力集中。
- 单个录制任务异常时，可能影响同一 GUI 进程里的其他任务。

对比“录画君”，它一个窗口只录一个直播间。需要同时录多个直播间时，用户会打开多个程序窗口。这个模型虽然朴素，但每个录制任务都在独立进程里运行，因此故障隔离更好。

## 2. 关键差异

### 2.1 故障隔离

- 录画君：一个窗口、一个进程、一个 ffmpeg/rtmpdump 录制任务。
- 本项目：一个 GUI 进程内管理多个主播、多个 ffmpeg 进程、同一个事件通道和同一套调度器。

结论：本项目的多路录制更容易被单进程内的事件风暴、状态竞争、日志积压影响。

### 2.2 日志处理

- 录画君：每个窗口只消费自己那一路 ffmpeg 输出。
- 本项目旧逻辑：后端把大量 ffmpeg stdout/stderr 逐行推给前端，再由前端过滤。

结论：过滤应尽量前移到后端。前端只应该接收关键生命周期日志、错误摘要和低频进度。

### 2.3 取流策略

- 录画君：优先从 `streamserver.php?target=...&mode=client&player=pc_web` 的 `tc-hls.streams.high / medium / low` 取明确的 HLS 地址。
- 本项目旧逻辑：OAuth `current_live` 优先，legacy 链路 fallback 时递归扫描 JSON 中的 URL 并打分。

结论：`tc-hls.streams` 是更明确的取流入口。OAuth 更适合补充标题、会员/保护状态、token 校验等信息。

### 2.4 录制参数

- 录画君默认使用 `-err_detect ignore_err -c copy`，输出多为 `.ts`，并提供自定义 ffmpeg 参数。
- 本项目使用 `ffmpeg -c copy` 输出 `.mkv`，并已加入 reconnect、headers、progress 解析。

结论：保留 `.mkv` 的稳定封装优势，同时补上 `-err_detect ignore_err`，后续可增加 `.ts` 兼容模式。

## 3. 已落地方向

短期优先修复不改变整体架构的高收益问题：

1. 后端过滤高频 ffmpeg 日志，避免 Wails 事件通道被刷爆。
2. legacy 取流优先读取 `tc-hls.streams.high / medium / low`。
3. ffmpeg 增加 `-err_detect ignore_err`，降低输入流小异常导致的录制中断概率。
4. “全部开始”增加错峰启动，避免大量主播同时检查和启动 ffmpeg。
5. 设置页增加画质策略、ffmpeg/ffprobe 路径配置。
6. `config.yaml`、`cookies.txt`、`download/` 作为本地运行数据忽略，并提供 `config.example.yaml`。

## 4. 下一阶段架构建议

推荐将“多主播统一 GUI”改造成“主 GUI + 单主播 worker 进程”的模型：

```text
主 GUI 进程
  -> recorder-worker.exe --streamer icy_muce
  -> recorder-worker.exe --streamer example_user
  -> recorder-worker.exe --streamer other_id
```

worker 进程只负责一个直播间：

- 检查直播状态。
- 解析 HLS 地址。
- 启动和停止 ffmpeg。
- 自动重连。
- 写入状态文件或通过本地 IPC 回报状态。

主 GUI 只负责：

- 管理主播列表。
- 启动/停止 worker。
- 展示每个 worker 的状态、进度和历史。

这样既能保留一个统一管理界面，又能获得“录画君多开窗口”式的进程隔离稳定性。

## 5. 后续可选功能

- 每主播画质策略：自动 high/medium/low、稳定中档、固定档位、保持原始。
- 输出容器策略：默认 `.mkv`，兼容模式 `.ts`，后处理转封装 `.mp4`。
- 每主播最近日志缓存：默认不推送高频日志，用户点开诊断时再读取最近 50-100 行。
- worker 崩溃自动拉起：主 GUI 记录退出码和最后错误，并可按策略重启。
